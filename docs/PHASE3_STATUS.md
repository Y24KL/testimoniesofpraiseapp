## What changed

**Tools the assistant can use.** All reads run with the signed-in person's own token, so Firestore rules apply.
- `search_testimonies`, `search_clips`, `open_screen`: unchanged in behaviour.
- `search_lyrical`: published lyrical analyses, ranked by title, song, artist and description.
- `search_articles`: published articles, ranked by title, category and body.
- `get_live_status`: whether the broadcast is on, and its programme title. It gives no schedule.
- `list_recent`: testimonies, articles and lyrical analyses published in the last 7 days, newest first.

**Verified cards.** Each tool result that finds real content adds a card: kind, id, title, subtitle, a deep link, and `verified: true`. Cards are built only from records the tools read. The model is shown titles and descriptions only, never ids or links, so it cannot invent or copy a card. At most 8 cards per answer. The app checks each card's shape and opens it by kind and id, not by link text.

**Answers.** The reply is still generated by Praxiom and is shown as before. The cards appear beneath it under "Found in Testimonies of Praise".

**Safety.**
- Stored text is treated as data. Control characters are removed, and length is capped. A test confirms that an instruction hidden in an article title does not open a screen.
- At most 6 data reads per turn, however many tool calls the model asks for.
- Over-long or malformed tool arguments are refused before any read.
- The app and the Worker share one list of screens, and a test checks they match.

**Firestore.** Two new composite indexes (`isPublished` with `publishedAt`, for testimonies and articles). Without them, the recent-content query fails in production. Rules require `isPublished == true` on these queries, so the query includes that filter.

**Compatibility.** The answer keeps `testimonies`, `clips`, `navigate` and `sources`, so older app builds keep working. They ignore `cards`.

**App.** Two new starter prompts ("What is new this week?" and "Recommend something"). Saved chats keep their cards.

## Decisions taken

- **Praxiom's tool-call format is taken as the existing code's OpenAI shape.** The assistant already uses it, and the docs say the API follows the OpenAI format. It is still unverified against the live API, which needs a test key. The parser is defensive, and a wrong shape would show as an error, not a fabricated card.
- **Lyrical analyses have no publish time.** "Recent" uses when they were last updated, so an edit to an old analysis can make it look new. The dedupe rules from Phase 1 do not apply here, because nothing is sent by this path.
- **No schedules.** Radio and event times are not in the app's data, so the assistant says it does not have them. The spec's "What is happening this week?" is answered with live status and recent publications only.
- **Lexical ranking, not embeddings,** for lyrical analyses and articles. Neither has embeddings yet, and adding them is a separate indexing job. Testimony search still uses bge-m3, as before.

## Known limits

- **Mobile only.** The website assistant still reads the old fields and ignores cards.
- **Ranking is simple.** Word matching finds only exact words, not synonyms. It is adequate for titles, not for meaning.
- **Read pool is 100 items.** Searches look at the 100 most recent published lyrical analyses and articles, so older items are not found by search yet.
- **The caveat on generated text** is a card heading, not a label on each reply. Make it more explicit if review asks for it.

## Deployment

1. Build the Firestore indexes (`firebase deploy --only firestore:indexes`). The recent-content query fails until they exist.
2. Deploy the Worker after `npm test`.
3. Test on staging with a test Praxiom key: ask for lyrical analyses, articles, what is new, and whether the broadcast is live. Confirm that a card opens the right screen and that a question with no match gets an honest "not found".
